# Repository workflow

- Follow CONTRIBUTING.md, SECURITY.md, and docs/release-verification.md.
- Preserve the five required main checks: Swift package tests; App build, UI tests, and layout; Real simulator end-to-end test; Release packaging; Analyze Swift.
- Run the applicable commands in CONTRIBUTING.md. Preserve warnings-as-errors, real simulator execution, UI tests, rendered layout checks, and release verification.
- Verify a successful Swift CodeQL analysis at the candidate revision. An older scan or successful Actions analysis does not validate new Swift code.
- Releases are version 1.x or later from main. Confirm the tag, ToolkitVersion.current, MARKETING_VERSION, and exact candidate revision before publishing.
- A v[1-9]* tag push starts release publication through .github/workflows/release.yml; obtain authorization covering publication before pushing it, and retain owner approval on github-release.
- Source extraction and analysis use read-only tokens with upload: never and upload-database: false. Separate upload-only jobs publish SARIF; Code scanning uploads must succeed for every configured language.

## Project-specific working defaults

- Treat `/Users/macbookpro/Codex/WORKSPACE.md` as the authority for the canonical checkout. Before changing files, read it, this file, any applicable `AGENTS.override.md`, `TODO.md`, project documentation, and the latest project checkpoint or continuity record. Verify the canonical Git root, branch, `HEAD`, remote, upstream, attached worktrees, open pull requests, and staged, unstaged, and untracked state. Preserve unrelated work.
- For work implemented and verified in this project, normal delivery is authorized: stage only reviewed task files or hunks, create focused conventional commits, use a `codex/` branch when appropriate, push ordinary non-force updates to the verified GitHub repository, and create or update a pull request. Use a pull request by default for source, behavior, packaging, workflow, dependency, security-sensitive, or substantial multi-file changes. A direct push is acceptable only on the correct non-protected task branch when it follows repository practice and does not bypass review or protection.
- Before every commit or push, re-confirm the canonical repository, branch, remote, upstream, `HEAD`, outgoing diff, and preserved unrelated state; inspect the complete staged diff; check for credentials, private evidence, device identifiers, personal data, local absolute paths, backups, logs, downloaded indicators, build caches, and private test artifacts; run applicable tests, linting, documentation, packaging, and native UI checks; review the final diff; fetch and inspect the verified remote before integration; push only the intended branch; and verify the resulting revision and GitHub checks. Never use `git add .`, `git add -A`, or `git commit -a` in a dirty checkout.
- If the canonical checkout has overlapping or conflicting user work, preserve it and use a suitable existing review worktree or a focused worktree from the correct committed base. Do not reset, clean, stash, discard, overwrite, or silently include unrelated changes.
- This standing delivery authorization does not cover merging pull requests, force-pushing or rewriting published history, deleting remote branches, creating tags or releases, publishing artifacts, deploying, approving protected environments or publication jobs, changing repository settings or permissions, broadening GitHub App access, or sending unrelated external messages. Obtain separate authorization for those actions.
- Do not start adapters, dependencies, installers, packaging, or CI work while an actionable TODO remains. Continue the established TODO order and distinguish local implementation and verification from physical-device, hosted-candidate, distribution, and publication acceptance.
- Maintain continuity during active work. At session start, load the latest safe project memory and checkpoint. At least hourly while actively working, and again before ending or pausing, update the existing checkpoint or continuity location with the objective and scope, canonical checkout/worktree, branch and `HEAD`, remote/upstream, pull request, Git state, intentional changes, completed and remaining TODOs, implementation decisions, exact test/build/CI/native outcomes, app bundle and native-window evidence when applicable, investigated failures, blockers, and next safe action. Do not store credentials, signing material, device identifiers, raw backups, private logs, personal information, or large command output in memory; avoid empty or repetitive entries.
- When completing work, report what changed and why, commit hashes and pushed branch, pull-request URL and review state when applicable, exact tests/builds/CI outcomes, remaining TODOs and blockers, updated-app path and visible state when applicable, and any publication-sensitive step that still needs authorization.
